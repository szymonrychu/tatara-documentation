
- 2026-08-16 (tatara-operator#604 fan-out, a published remedy the API refuses to give) **`mr-takeover.md` told a maintainer to push, and the 409 they are holding tells them not to.** The take-over conflict has TWO populations and one remedy each, and the page gave the decline's remedy to both. Only `implement-declined` is rewritten to `ownership-lost` when the branch comes back (`parkOwnerTask`); every other stopping reason survives the push untouched, so pushing and asking again returns the identical conflict, and while the merge request stays open only `ParkRetention` clears those. Two traps found while writing the replacement, both the enumerating kind this PR kept hitting: naming `ci-red` as the red-CI case is wrong (`stage.CIRed` writes it only when an owned MR has already MERGED, and a merged MR is refused by an earlier check, so the reason a maintainer actually sees is the re-entry cap), and "exhaustion limits" names three park reasons that have had no writer since they were retired. The page now describes the shape - CI that would not go green, a head that kept moving, a re-entry cap - instead of naming reasons it cannot keep true. Second-order and worth keeping: the conflict can never actually name a decline, because before a push nothing can reach the endpoint (the declined Task holds the merge request and runs no agent) and after a push the reason is no longer a decline - so the section that got the push remedy right described the case where the conflict cannot fire, and the section where it does fire got the remedy wrong. **The lesson: when a page states a remedy, check it against the string the API returns, not against the mechanism it documents** - the operator's own 409 body said "nothing clears this park" for six rounds while this page said "push".
- 2026-08-16 (tatara-operator#609 fan-out, one word meaning two things in one turn) **`mergeable` is now TWO different fields with two different definitions, and an agent sees both in the same turn.** The `MergeRequest` CR mirror's `mergeable` is the forge's own answer; the `mergeable` in a `scm_read(kind="ci")` response means **no-conflicts AND not-red** since tatara-operator#609, because GitLab's `merge_status` answers only "are there conflicts" and reports `can_be_merged` on a failed pipeline. `merge-request.md` said "whether the forge reports the PR/MR as mergeable", which is now true of exactly one of them. Also corrected in `mcp-tools.md`: `status` in a `kind=ci` response is NOT a fold over `checks[]` - it is the head pipeline's own aggregate, which the forge computes across child pipelines, retries and `allow_failure`, and folding the job list instead is precisely what shipped `green` on a failed pipeline (GitLab's `/pipelines/{id}/jobs` omits the `trigger:` bridge jobs that carry a child pipeline's result). Two row types in `checks[]` now carry no `logTail` even when failed - a bridge (its `url` is the downstream pipeline) and an external commit status (its `url` is the reporter's page) - and `none` means no CI observation at all rather than "no pipeline". **The lesson for this repo is the naming one:** a reference table describing a field by NAME rather than by ORIGIN silently starts describing the wrong field the moment a second surface grows the same name, and a doc that contradicts what an agent reads from the tool is tech-debt landing straight in its context (rule 4).
